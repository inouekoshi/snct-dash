# 材料工学科ステージ（学科ID=5）「鍛えてカン！」設計書

材料工学科ステージを作り直すための設計書。開発担当（人またはエージェント）がこれだけを読んで実装できるように、ルール・数値・触るファイル・受け入れ条件まで書く。

- 状態：実装完了（2026-10-16）
- 対象：`dev` ブランチ（デモ版）だけ。**`main`（本番）には触らない**。本番リリースは材料工学科の完成後に別途行う
- デモ版での材料工学科のメンテナンス設定（`NEXT_PUBLIC_MAINTENANCE_DEPARTMENTS=5`）は解除済み。全5学科がプレイ可能。

1〜3章で何を作るかを、4〜6章でどう作るかを書いた。数値は7章の表にまとめてある。

---

## 1. タップでハンマーを振り、焼けた金属をぴったりのタイミングで叩く

このステージだけ、タップは「ジャンプ」ではなく「ハンマー」になる。地面を赤く焼けた金属の塊が流れてくるので、キャラの前にある輪に重なった瞬間にタップして叩く。ぴったり叩くと「カン！」と火花が散って塊が板になり、安全に駆け抜けることができる。連続で成功するとコンボが加算される。叩きそこねた塊にはぶつかり、後ろに戻される。

タップで「叩く」のは5学科でこのステージだけになる（ジャンプしないのは、長押しで泳ぐ生物応化とこのステージだけ）。ほかの学科とは、やること（動詞）がはっきり違う。

| 学科 | やること |
|---|---|
| 機械 | 階段状の山と障害物をジャンプで越える |
| 電気電子 | 減り続ける充電を、空中の電池をジャンプで拾って保つ |
| 電子情報 | バグを上から踏んで倒し、3匹でデバッグモード |
| 生物応化 | 長押しで浮かび、すき間をくぐる |
| **材料（新）** | **流れてくる金属を、タイミングよく叩く** |

## 2. 前の案は「ルールを読む作業」が多く、気持ちいい瞬間が少なかった

前の案「製品ができるまでラン」は、ユーザーに「シンプルに面白くない」と却下された。原因はこう見ている。

- 工程ごとにルールが変わり、1つの遊びを味わう前に次へ移る
- 熱処理の「看板を見て、ゲートを選び、課題に備える」は読む作業で、反射で遊べない
- 唯一の快感である板バネの加速は、0.3秒減速してから来るので弱い

そこで今回は、次の順に評価して案を選んだ。

1. 5秒で分かり、気持ちいい瞬間が1プレイ（約100秒）に何十回も来ること
2. ほかの4学科とやることが被らないこと
3. 材料工学科らしさに、鈴鹿高専の公式情報の根拠があること
4. 残り約2週間で作って調整できること

叩き台7案を、批評エージェント3体（ゲームデザイン・来場者体験・実装）で2ラウンド批評した。「鍛えてカン！」は3体とも8点（10点満点）で、作る手間もいちばん小さかった。ほかの案は10章にまとめた。

学科とのつながりの根拠は、鈴鹿高専公式サイトの教員一覧にある研究キーワード「加工熱処理」（万谷義和教授・黒田大介教授）と「結晶粒微細化」（黒田教授）。

## 3. 遊びのルール（確定仕様）

### 3-1. 入力：タップ1つで叩く。ジャンプはしない

- タップ（スペース・↑キー・クリックも同じ）でハンマーを振る
- 自キャラは常に地面を走る。重力と着地の処理は今のまま動かしてよい（ずっと接地している）

### 3-2. 判定はフレームで決め、遅い側を広くとる

塊の**中心**が輪の中心に届くまでの残りフレーム数を `t` とする（`t = (塊の中心x − 輪の中心x) ÷ 今の実効速度`）。`t` は小数のまま扱う。正の値は、塊がまだ輪に届いていないこと、つまり早いことを表す。見た目の予告の輪（3-5）も塊の中心に描くので、輪がぴったり重なって見える瞬間が `t` = 0 になる。

タップしたら、まだ叩いていない塊のうち `t` ≥ −6.5 のもので一番近いものを選び、その `t` で判定する。`t` < −6.5 の塊（判定を過ぎて自キャラに向かっている塊）は対象から外し、そのままぶつかって「おそい！」になる。

| `t` の範囲 | 判定 | 結果 |
|---|---|---|
| −2.5 ≤ `t` ≤ +2.5 | PERFECT | 塊が板になって飛ぶ。連続回数 +1。ヒットストップ2フレーム。「カン！」を大きく表示 |
| +2.5 < `t` ≤ +4.5（早め）／ −6.5 ≤ `t` < −2.5（遅め） | GOOD | 塊は板になる。連続回数 +1。「コン」を小さく表示 |
| +4.5 < `t` ≤ +20 | はやい | 空振り扱い（下の表）。「はやい！」を表示。12フレーム硬直（連続回数は維持） |
| 対象の塊がない（どれも +20 より遠い） | 空振り | ハンマーを振るだけ。罰はなし（12フレーム硬直だけ入る） |

- 遅い側を広くしているのは、スマホのタッチの遅れを吸収するため。固定の遅延補正は端末ごとの差が大きいので入れない
- 判定はピクセルでなくフレームで決める

空振りと失敗の扱いは次のとおり。

| 起きたこと | 結果 |
|---|---|
| 「はやい」空振り | 12フレームの硬直（この間は叩けない。連続回数は維持） |
| 罰なしの空振り | 12フレームの硬直だけ |
| 叩けなかった塊が自キャラに当たる | いつものノックバック（`knockback(KNOCKBACK_AMOUNT)`）。連続回数を0に戻す。「おそい！」を表示 |

この組み合わせで、連打は損になる。早めに連打すると硬直が入り、その間に塊が来てぶつかるからだ。2連・3連の塊どうしの間隔（18フレーム）は硬直（12フレーム）より長くして、硬直と重ならないようにする。

### 3-3. 等速リズムアクション仕様と最大連続ボーナス

- テンポよく塊を叩いて板にして進むリズムアクションとするため、速度変化（ブースト）は行わず等速（`MAT_BOOST_MAX = 1.0`）とする
- 完走時の走行タイムは約104.8秒となる
- **最大連続ボーナス**：走行中に達成した最大連続回数 × 100ms（0.1秒、`FORGE_COMBO_BONUS_MS`）をクリアタイムから差し引く。フルコンボ（約173回）時は約17.3秒短縮され、最終記録は**約87.5秒**（電子情報工学科の約89秒と並ぶ最速クラス）となる
- `limits.ts` の材料工学科の下限タイムは `80_000`（80秒、理論値 約87.5秒）に設定
- 位置を直接進める効果（前に飛ばすなど）は使わない。理論最短の計算に乗らないため

### 3-4. 最初の数秒で「叩くんだ」と分からせる

他学科で「タップ＝ジャンプ」を覚えた来場者は、始まってすぐタップする。それを説明に変える。

1. 開始から1.5秒は塊を出さない。画面上部の中央に「タップでたたけ！」とハンマーの絵を出す。この間のタップは、ハンマーを大きく振る動きと風切りの線だけを見せる（罰なし）
2. 最初の2個の塊は、`t` ≤ +4.5 になったら世界を20%の速さにし、輪を点滅させて待つ。タップすれば PERFECT 扱いにする。2秒待ってもタップがなければ、通常の速さに戻す。タイマーは止めない（全員同じ条件なので、タイムの公平さは保てる）
3. 3〜5個目の塊は単発で、間隔を広くとる

### 3-5. 叩くタイミングを目で予告する（音に頼らない）

会場ではスマホの音が出ない前提で作る。成否は画面だけで伝える。

- **予告の輪**：各塊の中心のまわりに輪を描き、塊が輪に近づくほど縮める。半径は「判定の輪の半径 × (1 + 2 × min(1, 塊の中心と輪の中心の距離 ÷ `FORGE_SPAWN_DIST`))」。画面に入った瞬間は3倍の大きさで、`t` = 0 でちょうど判定の輪と重なる（osu! の収縮円と同じ）。

### 3-6. 塊の出方：パターンを4つの区間で濃くしていく

出現の間隔は距離ではなく**時間（フレーム）**で決める。速度が8→15と上がっても、手で叩く間隔が変わらないようにするためだ。

- スポーナーは「次の塊が輪に届くまでの残りフレーム」を予定の列（キュー）として持ち、1ずつ減らす。減らすのは `update()` がヒットストップとミス表示の確認を抜けて物理を進めるフレームだけ。チュートリアルで世界を遅くして待っている間（3-4）も減らさない。パターンを選んだら、その中の塊の到着予定（例：2連なら 残り, 残り+18）をまとめて列に積む
- 残りフレーム × 今の実効速度 ≤ 560（`FORGE_SPAWN_DIST`。輪の中心 x=285 から x=845 までの距離）になった時点で、塊の中心を x = 285 + 実効速度 × 残りフレーム に置く。置く位置の計算には、チュートリアルの減速をかける前の実効速度を使う
- ただし置く位置は **max(845, 285 + 実効速度 × 残りフレーム)** にして、x=845 より手前には置かない。ノックバック後の復帰（速度8）で速度が急に下がったときに、まだ置いていない塊の「残り × 速度」が一気に560を割り、画面の内側に出てしまうのを防ぐため。x=845 に置いた塊は予定より少し遅れて輪に届くが、判定は実際の位置で決めるので問題ない
- 最初に条件を満たすフレームで中心が 845 − 速度 より右にある。最高速（15px/フレーム）でも塊の左端は x=810 より右、つまり画面（幅800）の外から入ってくる

| パターン | 中身 |
|---|---|
| 単発 | 塊1個 |
| 2連（タタン） | 塊2個。間隔18フレーム |
| 3連（タタタン） | 塊3個。間隔18フレーム |
| 休み | 塊なし。40〜60フレーム |

ステージを進み具合で4区間に分け、後ろの区間ほどパターンを詰める。

| 区間（進み具合） | 出るパターン | パターン間の間隔 |
|---|---|---|
| 0〜25% | 単発中心、2連が少し | 50〜70フレーム |
| 25〜50% | 単発・2連 | 40〜60フレーム |
| 50〜75% | 2連・3連 | 34〜50フレーム |
| 75〜100% | 3連中心。最後の約10秒は一番密度を高く | 30〜44フレーム |

- 区間の切り替わりには約1秒の休みとカットインを表示して区切りを見せる
- 同じパターンが続きすぎないよう、ほかの学科と同じシャッフルバッグ（`ShuffleBag`）で選ぶ

**任意（後回しでよい）：巨大な塊。** 輪に届くとスクロールが止まり、1.5秒以内に4回叩くと砕ける（ドラムロールのような山場）。失敗するとノックバック。中心の遊びが調整できてから検討する。

### 3-7. 手応えは光と揺れと大きな文字で伝える

- PERFECT：ヒットストップ2フレーム、火花、画面の小さな揺れ、「カン！」の大きな文字。叩いた塊は光る板になって後ろへ飛ぶ（既存のパーティクル `burst` を使う）
- GOOD：「コン」を表示。塊は板になる
- はやい：「はやい！」を表示。12フレーム硬直
- 連続回数（PERFECT と GOOD の連続）を画面上部の中央に大きな数字で出す
- 判定の文字・連続回数・予告は、画面の左下・右下（親指で隠れる場所）に置かない

### 3-8. 見た目：大きなハンマーを担いだキャラと、粒々の塊

- **自キャラ**：今の自キャラに、長い柄のハンマーを担がせる。ほかの学科とシルエットで区別できるようにする。振りの動きは約8フレーム
- **塊（`hot_ingot`）**：赤く光る四角い金属塊。表面に大きな粒々の模様を描く。高さは約40px、地面に置く
- **叩いた後の板**：薄い板。粒々の模様を細かくして描く。研究キーワード「結晶粒微細化」を絵で表すための演出。文章で「叩くと粒が細かくなる」とは言い切らない（9章）
- **背景と地面**：材料用の背景「材料の宇宙」（`bgMat`、星空とオーロラ）と地面（`drawMatGround`）を使う
- **塊の大きさ**：幅40px（`FORGE_INGOT_W`）、高さ約40px
- **輪の位置**：輪の中心は自キャラの175px前（x = `PLAYER_X` + 175 = 285）、高さは塊の中心に合わせる。この距離は次の計算で決めた
  - `t` = 0 のとき塊の左端は x=265。塊が自キャラに当たるのは、当たり判定の左端（塊のx + 4）が自キャラの前端 x=122 を割ったとき、つまり塊のx < 118 になったとき。そこまで147px
  - 最高速（15px/フレーム）でも、遅い側の判定の終わり（6.5フレーム＝97.5px）までは当たらない
  - 輪を近づけたり塊の幅を変えたりするときは、この計算をやり直す
- ハンマーの柄を長く描き、輪まで届いて見えるようにする

### 3-9. ゴールと結果画面

- ゴールの演出で、最大連続回数をキャンバスに描く（`goal-renderer`）。クリア結果の型（`GameClearResult`）には足さない。足すと結果画面と API まで改修が広がる
- 結果画面の `components/MatProductReveal.tsx` は、眼鏡フレームの演出を、粗い粒の塊と細かい粒の板を並べた絵に差し替える（研究キーワード「結晶粒微細化」を表す絵。因果を文で言い切らない）。添える文は公式情報に根拠のあるものだけにする（9章）。例：「鈴鹿高専の材料工学科には、『加工熱処理』や『結晶粒微細化』を研究している先生がいます」

## 4. 実装：エンジンの材料分岐を差し替える

### 4-2. 足すもの

| ファイル | 内容 |
|---|---|
| `lib/game/constants.ts` | 7章の `FORGE_*` 定数 |
| `lib/game/engine-types.ts` | 障害物の形 `hot_ingot`。障害物に `struck?: boolean`（叩いた塊を二重判定しない）、`tutorial?: boolean`（3-4 の最初の2個） |
| `lib/game/engine.ts` | 状態：`forgeCombo`、`forgeMaxCombo`、`strikeCooldown`、`swingTimer`、判定文字の種類と表示タイマー、チュートリアルの待ち状態。メソッド：`strike()`（3-2 の判定）。`jump()` の中で、今ある「クリア後・一時停止中・ミス表示中なら何もしない」の確認（`if (this.isCleared || this.isPaused || this.missOverlayTimer > 0) return`）の**直後**に `if (this.isMat) { this.strike(); return }` を置く。`effectiveSpeed` は等速（ブーストなし）。`knockback()` で `forgeCombo = 0`。`snapshot` に `forgeCombo` を足す（ボットとテスト用） |
| `lib/game/spawner.ts` | 材料用のパターン（3-6）。時間基準で塊を置く `forge()` |
| `lib/game/obstacle-drawers.ts` または `mat-renderers.ts` | `hot_ingot` の描画（粒々・赤熱）、予告の輪、判定の輪、ハンマーと振りの描画、判定文字、連続回数 |
| `lib/game/autopilot.ts` | 材料のときだけ3連用の候補（`[0, 18, 36]` など）を足す（下の 4-4） |

注意点が4つある。

- **ヒットストップ中の入力**：`jump()` は、クリア後・一時停止中・ミス表示中の入力は捨てているが、ヒットストップ中の入力は止めていない。`strike()` の先頭で、PERFECT のヒットストップ（2フレーム）の間のタップを無視する
- **ヒットストップとタイム**：`update()` はヒットストップ中に `elapsedMs` を加算せずに戻る。PERFECT の演出でタイムが損も得もしないので、そのままでよい
- **複製（`clone()`）で状態を共有しない**：ボットは毎フレーム `engine.clone()` で先読みする。`clone()` は浅いコピーで、作り直しているのは `obstacles`・`items`・乱数・`spawner` だけ。`Spawner` の複製もバッグしかコピーしない。新しく足す予定の列（3-6）は、`Spawner` のコンストラクタの `from` 側で配列を複製する。エンジンに足す状態のうち配列やオブジェクトのものも、`clone()` で複製する。そうしないと、先読みが本体の列を減らしてしまう
- **硬直と先行入力**：既存のジャンプの先行入力（`jumpBuffer`）は、材料では使わない。硬直中のタップは捨てる（先行入力にすると連打が有利になる）

### 4-4. 自動プレイのボット：今の候補に3連用を足すだけでよい

- ボットは毎フレーム計画を立て直し、候補には毎回「今押す」（`[0]`）が入っている。なので今の `JUMP_PLANS` のままでも、どのフレームでも叩ける（PERFECT の幅5フレームより刻み3フレームのほうが細かい）。`jump()` が `strike()` に回るので、ボット側の入力はそのままでよい
- 足すのは3連用の候補だけ：材料のときに `[0, 18, 36]` と `[k, k+18, k+36]`（`k` = 3〜15 を3刻み）を候補に加える。2連用の `[0, 18]` は今の候補に入っている
- 評価関数は進んだ距離とミス数に加えて、連続回数（`end.forgeCombo * 20`）を評価する
- チュートリアルの待ち（3-4）の間も、ボットが叩いて進めることを確かめる

## 8. 実機で確かめて調整すること

- PERFECT の幅（±2.5）が、スマホのタッチで狙えるか。厳しすぎたら ±3.5
- 遅い側の GOOD（−6.5まで）で、タッチの遅れを吸収できているか
- 後半の区間で、予告の輪だけでリズムがつかめるか
- 100秒やって飽きないか。飽きるなら、区間ごとのパターンの密度と見た目の変化を強める（ルールは増やさない）
- 輪（画面の左から約36%、上から約7割の位置）が、横持ちの左手の親指で隠れないか。隠れるなら輪とキャラの距離を広げる
- クリアタイムが、生物応化を除くほかの学科（自動プレイで約89〜105秒）と大きくずれていないか

## 9. 文言の規則

- 学科についての文（学科紹介・結果画面の一言）は、鈴鹿高専の公式サイトと各学科サイトに書かれていることだけで書く。一般常識で補わない（例：「結晶の粒を細かくすると金属が強くなる」は公式サイトに書かれていないので使わない）
- ステージの説明は、ゲームの実際の挙動と一致させる（数値・色・操作）
- 日本語の文は natural-japanese スキルで確認する。文言を変えたら、別のエージェントに原文とコードとの突き合わせ（ハルシネーションチェック）をしてもらう
