# 高専ダッシュ！ ロードマップ — 進化の方向性

このドキュメントは、ゲームをより魅力的・持続的に楽しんでもらうための進化方針をまとめたものです。
初稿に対し、3つの観点（ゲームデザイン / 高専祭運営 / 実装可能性）からフィードバックを反映した第2版です。

---

## 1. ビジョン

> **「鈴鹿高専祭の来場者が、15分の空き時間に何度も挑戦したくなる、5学科の魅力が詰まったランナーゲーム」**

3つの柱：
1. **触りやすさ**：1タップで遊べる、説明不要のシンプル操作
2. **奥深さ**：上手いプレイヤーが「もう一回」と思える戦略性とリスク選択
3. **高専らしさ**：5学科のアイデンティティが感じられるテーマ性

---

## 2. 現状の評価

### 良い点
- ジャンプ1操作で完結する直感的なゲームプレイ
- 5学科それぞれが視覚的に区別された世界観
- 周回・天井障害物で難易度の天井を解消
- リーダーボードによるソーシャル要素（全期間TOP20・当日TOP10のJST対応済み）
- 音声ファイル0個・軽量で低スペック端末でも動作
- コヨーテタイム・先行入力バッファで「理不尽な死」を大幅削減
- ヒットストップ・画面シェイク・コイン音階上昇で爽快感が向上
- スコア倍率システムでノーミスプレイへのインセンティブが生まれた

### 課題
- **モチベーションが「ハイスコア更新」だけ**：プレイ後に何も残らない
- **学科の特色が背景・色のみ**：ギミックレベルでの差別化がない
- **イベント性の薄さ**：高専祭という場の特性が活かされていない
- **スパム対策が未実装**：祭当日に不正スコアが入り順位表が汚染されるリスク

## 3. 進化の方向性

### A. 短期施策 ─ フェアネス＆プレイ感最優先（実装済み・見送り）

| # | 施策 | 状態 | 概要 |
|---|-----|------|------|
| **A2** | **コヨーテタイム＋ジャンプ先行入力バッファ** | ✅ 実装済み | 地面から離れた直後5フレームの猶予 / 着地直前のジャンプ入力を8フレーム保持して自動実行 |
| **A3** | **ジューシーフィードバック群** | ✅ 実装済み | シールドヒット時0.1秒ヒットストップ／コイン連続取得で音階上昇／エリア遷移演出強化 |
| **A5** | **スコア倍率の組み込み** | ✅ 実装済み | ノーミスエリア完走で ×1→×2→×3。ダメージで×1にリセット。HUDとエリア遷移画面に表示 |
| ~~A1~~ | ~~ニアミス報酬~~ | ❌ 見送り | 1ジャンプ操作では「自動で積み上がる数字」になりがちなため削除 |
| ~~A4~~ | ~~ボーナスゾーン~~ | ❌ 見送り | 現フェーズでは不要と判断 |
| ~~A6~~ | ~~チュートリアル改善~~ | ❌ 見送り | 現フェーズでは不要と判断 |

> **方針転換の理由**：当初A1だった「コンボシステム」は、Subway Surfersのような多操作ゲームでは効くが、1ジャンプ操作のゲームでは「自動で積み上がる数字」になりがち。Geometry Dashにコンボ表示がない理由を踏まえ、倍率としてスコア式に組み込むだけに縮小。A1（ニアミス報酬）・A4（ボーナスゾーン）・A6（チュートリアル）は当面見送り。

### B. 中期施策 ─ メタ進行で「もう一回」を生む（1〜2週間）

| # | 施策 | 効果 | 概要 |
|---|-----|------|------|
| **B1** | **カケラ（Fragment）収集メタ進行（最優先）** | リプレイ動機 ↑↑ | エリアごとに極稀（1プレイで0〜2個）に出る学科シンボル（歯車、回路、DNA等）を集めると、タイトル画面で5学科のシルエットが徐々に色づく。**累積永続**なので「あと1個で機械工学科コンプリート」が次プレイ動機になる。localStorage完結でサーバー改修不要 |
| **B2** | **アチーブメント** | 反復動機 | 「Lap 3達成」「コイン100枚」「ノーミスでArea5到達」「倍率×3でエリアクリア」など。バッジコレクションでカケラと相互補完 |
| **B3** | **学科別ギミック差別化** | 高専らしさ ↑↑ | 色替えではなく報酬系で差別化。例：電気電子=コイン取得で回路が繋がり一時加速／生物=試薬3色集めで爆発スコア／材料=シールドが結晶化して2発耐える。**コア操作（ジャンプ）は壊さず、エリアごとの報酬の意味を変える** |
| **B4** | **リザルト画像シェア** | 拡散 ↑ | Next.js 標準の `ImageResponse` でスコア・到達エリア・周回・カケラ進捗をOGP画像化し、X / LINE で共有 |
| **B5** | **学科選択モード** | コミット感 | プレイヤーが学科を選んで参加。スコアが学科に集計される（要DB拡張：[5章](#5-db設計の進化) 参照） |

### C. 高専祭イベント特化 ─ 「物理×デジタル」を重視

| # | 施策 | 効果 | 概要 |
|---|-----|------|------|
| **C1** | **物理ポスター順位表（紙×ゲーム連動）** | バズる・止まらない | 会場入口に5学科の縦長ポスター（巨大温度計型）を貼り、運営学生が30分ごとにマジックで学科合計スコアを塗り上げる。**通信不要・写真映え・運営止まらない**。デジタルモニターより圧倒的に強い |
| **C2** | **カテゴリ別ランキング** | 包摂性 | TOP20だけだと当日ピーク時に高校生上級者で埋まり、保護者・小学生・住民が永遠に載れない。「小学生以下／保護者世代／高専生」のカテゴリ別TOP10を併設 |
| **C3** | **学科ボス撃破→リアル景品引換コード** | 送客 ↑ | ボス撃破時に4桁コードを画面表示→該当学科ブースで見せると缶バッジ等プレゼント。**ゲーム→展示への送客動線**が生まれ、各学科の集客課題も同時解決 |
| **C4** | **実物アセット化** | 在校生・卒業生に刺さる | 抽象アイコンではなく、各学科の実習機材・実験器具・先生の似顔絵シルエットを障害物に。「これ知ってる！」がシェアを生む |
| **C5** | **スパム対策・レート制限（必須）** | 順位表の信頼性 | 現状のRLSは "Anyone can insert" で祭当日にスパム耐性ゼロ。Edge Middlewareでレート制限（同IP 10req/min）と、device_hash (localStorage UUID) ベースの簡易紐付けが必須 |

#### ❌ 見送り（初稿から削除）

- ~~QR連携~~：各学科展示にQRを掲示し続ける運用負荷（剥がれたら貼り直す等）がオーナー不明になり破綻リスク大。**C3のボス→引換コード方式に置換**
- ~~タイムイベント~~：「14時にRUSH祭り」は分散ではなく**集中**を生む。直前に行列が崩壊し離脱者を増やすため、常時混雑分散を狙うべき

## 5. DB設計の進化

現状の `scores` 単一テーブルでは、学科対抗・アチーブメント・カケラ収集・スキン解除に対応不可。

### 提案スキーマ

```sql
-- プレイヤー（無記名対応、localStorage UUID で同一視）
CREATE TABLE players (
  id UUID PRIMARY KEY,
  nickname TEXT NOT NULL,
  device_hash TEXT UNIQUE NOT NULL,  -- localStorage UUID
  department INTEGER,                 -- 1〜5 学科ID（任意）
  created_at TIMESTAMPTZ DEFAULT now()
);

-- スコア（既存テーブルに player_id FK 追加）
CREATE TABLE scores (
  id UUID PRIMARY KEY,
  player_id UUID REFERENCES players(id),
  score INTEGER NOT NULL,
  distance INTEGER NOT NULL,
  max_area INTEGER NOT NULL,
  max_lap INTEGER DEFAULT 0,
  combo_max INTEGER DEFAULT 0,
  fragments_collected JSONB,          -- 取得カケラ
  played_at TIMESTAMPTZ DEFAULT now()
);

-- アチーブメント
CREATE TABLE achievements (
  player_id UUID REFERENCES players(id),
  achievement_id TEXT NOT NULL,
  unlocked_at TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (player_id, achievement_id)
);

-- 学科集計（高速化用マテビュー、pg_cron で5分更新）
CREATE MATERIALIZED VIEW department_scores AS
  SELECT department, SUM(score) AS total, COUNT(*) AS plays
  FROM players p JOIN scores s ON p.id = s.player_id
  WHERE p.department IS NOT NULL
  GROUP BY department;
```

### セキュリティ強化
- RLS は `service_role` をAPI経由でのみ書き込む形に強化
- Edge Middleware でレート制限（同IP 10req/min）
- device_hash + IP + UA で不正登録の検知

## 8. 設計原則

施策追加時は以下の原則に従う：

1. **5秒で楽しめるか**：高専祭の来場者は短時間で離れる。チュートリアル無しで遊べることを最優先
2. **学科の特色がギミックレベルで出ているか**：単なる色・名前変更ではなく、報酬系や操作の意味付けで差別化
3. **コア操作（ジャンプ）を壊さないか**：操作を増やすより、既存操作の意味付けを深める
4. **フェアネスを保つ**：プレイヤーが「理不尽に死んだ」と感じる瞬間をなくす。コヨーテタイム・先行入力バッファ・倍率リセットで「上手くなった」感を返す
5. **ジューシーであれ**：ヒットストップ・画面シェイク・効果音の重ね方を惜しまない
6. **「貯まる」感覚を残す**：プレイ後に何かが永続的に残る（カケラ、アチーブメント、ハイスコア）
7. **モバイル横向きで快適か**：実機（スマホ）での動作を常に基準にする
8. **オフライン動作の影響**：通信障害時もコアゲームは遊べる状態を維持

## 9. リスクと制約

| リスク | 内容 | 対策 |
|--------|------|------|
| **Supabase Free 同時接続60** | Realtime使うと祭当日に詰む可能性大 | leaderboard は `cache: 'no-store'` で取得、Realtime回避 |
| **Vercel Hobby の商用利用問題** | 規約上Pro必須の解釈あり | 高専祭運用前に要確認、必要ならPro契約 |
| **スパム・不正スコア** | 現状のRLSは "Anyone can insert"、祭当日に汚染リスク | C5のレート制限・device_hash紐付けをPhase 3で実装 |
| **学科対抗の集計汚染** | 自己申告では他学科を騙れる | 学科カラム＋device_hash紐付け、変更不可制約 |
| **当日ピーク負荷** | 同時数百人プレイ時のDB書き込み集中 | Edge Middlewareでレート制限、scoresは事前マテビュー化 |

## 10. 推奨ライブラリ・実装パターン

| 用途 | 推奨 | 理由 |
|------|------|------|
| OGP画像生成 | `next/og` の `ImageResponse` | Next.js標準、追加依存ゼロ |
| PWA | `app/manifest.ts` ＋ 手書き `public/sw.js` | `next-pwa` は Next 16未対応の可能性大 |
| ハプティック | `navigator.vibrate()` 直叩き | ライブラリ不要 |
| アナリティクス | `@vercel/analytics` | Hobby枠で動作 |
| クライアント永続化（カケラ等） | `localStorage` 直 | Zustand導入は過剰 |
| QR生成（C3引換コード用） | `qrcode` (Node) | `ImageResponse` 内に埋め込み |
